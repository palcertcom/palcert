# ADR-0123: The SSRF boundary pins DNS and classifies against committed IANA snapshots

- **Status:** Accepted
- **Date:** 2026-09-18
- **Phase:** 17

## Context

A webhook URL is an address a customer chose, and PalCert's workers sit inside
its own network. Every cloud metadata service, every internal admin panel and
every database is reachable from there by name or by address.

Two mistakes are standard. The first is a hand-written list of private ranges,
which is always missing something — carrier-grade NAT, IPv4-mapped IPv6,
`0.0.0.0/8`, the documentation ranges, IPv6 unique-local. The second is
validating the hostname and then handing it to an HTTP client, which resolves
it again: between the two lookups the name is free to change its answer.

## Decision

**Resolve once, classify every address against committed IANA registries, and
connect to the address that was checked.**

`SafeWebhookHttpClient` resolves the host itself, classifies *all* returned
addresses — not just the first — against generated snapshots of the IANA
IPv4 and IPv6 special-purpose address registries, and then connects by pinning
the checked address rather than by passing the name down.

The snapshots are generated by a script, committed to the repository, and
checked for drift in CI. Redirects are refused rather than followed, and the
response body is never read.

## Consequences

The guard is auditable: the ranges are a generated file with a provenance
comment, not a developer's recollection.

A registry update is a visible commit that CI notices, rather than a silent
gap.

It is also why the e2e suites cannot exercise a real socket: every address a
test sandbox can host is refused, correctly. The network edge is covered by
unit suites around the client, and the e2e suites cover everything on either
side of it.
