# Official submissions

Phase 14. How a private PalCert Check becomes something an institution has
formally received, and — just as importantly — everything that stays private
when it does.

The one sentence the whole phase is built around:

```
PRIVATE PALCERT CHECK  ≠  OFFICIAL INSTITUTION SUBMISSION
```

And the one beside it:

```
Technical Compliance  ≠  Institution Academic/Administrative Decision
```

## The workflow

```
Private document
      ↓  (paid, private)
PalCert Check  →  Technical report  →  optional SmartFix  →  updated report
      ↓
  the person reads what would be shared, and presses a button
      ↓
SUBMISSION_PREPARE — copy the exact bytes, verify, copy the report, verify
      ↓
Immutable official submission snapshot
      ↓
Organization review queue
      ↓
SUBMITTED → UNDER_REVIEW → APPROVED | REJECTED | REVISION_REQUESTED
                                                        ↓
                                              a new revision of the same case
```

Nothing before the button is visible to the organization. Nothing after it
reaches back past the snapshot.

## What is shared, and what is not

The disclosure shown before submission is generated by the server from the same
read the submission itself performs, so the promise and the act cannot drift.

**Shared:** this exact document version, the technical report for this check,
the determination, the score and the rule-by-rule findings, the standard and
version it was measured against, and the submitter's display name and email.

**Not shared:** any other version of the document, any other check, the AI
review, the SmartFix plan and manifest, the balance and payments, and every
other file in the account.

That second list is stated explicitly, in both languages, because "we only
share what you submit" is a promise nobody can verify and a list is one they
can.

## The data model

| Table | What it is |
| --- | --- |
| `official_submissions` | The long-lived case: one per (author, organization, document) |
| `submission_revisions` | One immutable official handoff. Monotonic per case |
| `submission_decision_events` | Append-only institution history. The authority |
| `submission_comments` | Immutable review comments, institution side only |

A revision binds one exact COMPLETED Check, its CheckRun and its CheckReport at
creation, and nothing is resolved by "latest" afterwards (ADR-0109). It carries
the source digests, the snapshot identities, the technical result copied for
queue display, and an evidence hash over all of it (ADR-0110).

### Two statuses, never one

`SubmissionProcessingStatus` (`PREPARING`, `READY`, `FAILED`) is PalCert's own
copying. `InstitutionDecisionStatus` (`SUBMITTED`, `UNDER_REVIEW`, `APPROVED`,
`REJECTED`, `REVISION_REQUESTED`) is the institution's. No value is shared, and
a storage-copy failure is never an institution rejection (ADR-0108).
`NOT_SUBMITTED` is a derived display state and is never stored.

A revision becomes `READY` and `SUBMITTED` together or not at all; a check
constraint refuses a row that has one without the other, the snapshot
identities and the evidence hash.

## Isolation

The submission tables are `DUAL_PARTY_SCOPED`, a fifth isolation class added
for rows that exist only because one party explicitly handed something to
another (ADR-0106). Both parties read; the policies say so rather than the
application remembering to.

Write authority is asymmetric and is not part of the class (ADR-0107):

| | `official_submissions` | `submission_revisions` | `submission_decision_events` | `submission_comments` |
| --- | --- | --- | --- | --- |
| SELECT | both | both | both | both |
| INSERT | author | author | organization, as itself | organization, as itself |
| UPDATE | author | author (identity) / organization (decision only) | nobody | nobody |
| DELETE | nobody | nobody | nobody | nobody |

Row-level security decides rows; it cannot decide columns, and both parties
share one database role. So a trigger on `submission_revisions` refuses any
organization-originated UPDATE that changes a column outside the institution's
own decision fields. It compares whole rows with those columns removed, so a
column added in a later phase is refused by default rather than silently
becoming organization-writable.

The discriminator is **context, not identity**. A caller with organization
context is acting as the institution; one without it is acting as the
submitter. That stays well defined when one person is both.

### What was not widened

`documents`, `document_versions`, `document_analyses`, `document_checks`,
`check_runs`, `check_reports`, the AI tables, the SmartFix tables and every
finance table remain `USER_SCOPED`, and the coverage suite asserts it. ADR-0031
stands: `OR organization_id = …` is forbidden on the author's private tables.
It never applied to a table that exists only because the author created it to
hand something over.

## Preparation

`SUBMISSION_PREPARE` is a durable job written in the same transaction as the
revision it describes. Submission returns 202; the organization sees nothing
until the copy is verified.

1. **Claim** — only a `PREPARING` revision is worked on, so ten deliveries
   produce one snapshot pair and one `SUBMITTED` event.
2. **Verify the source** — read and hash the document against the digest the
   check recorded, and the report artifact against its own. An institution must
   never be handed evidence PalCert did not re-check at the moment of handing
   it over.
3. **Copy exactly** — a server-side copy of one exact object version to an
   organization-scoped key. Nothing is rendered, re-encoded, rebuilt or
   regenerated.
4. **Verify the copy** — read the destination back and hash it. A copy that
   differs fails closed.
5. **Finalise** — snapshot identity, evidence hash, `READY`, `SUBMITTED`, the
   `null → SUBMITTED` SYSTEM event and the case pointer, in one statement.

Step 5 goes through a narrow `SECURITY DEFINER` function, because writing
`SUBMITTED` is institution-decision authority that the submitter's context does
not have and must not be given. Recognition as the system writer requires both
a role switch only that function can reach and a transaction-local flag; the
flag alone is forgeable by the application role and buys nothing.

A preparation failure sets `processingStatus = FAILED` with a failure code and
never touches the decision status.

## Storage

Snapshots live in the `derived` zone under
`organizations/{orgId}/submissions/{submissionId}/revisions/{revisionId}/{document|report}`
— organization-scoped, with no name, email or title in the key. There is no
public ACL and no public CORS. Both parties fetch through a short-lived signed
GET, and the filename an institution receives names the submission rather than
the author's own file.

## The decision

Authorization is by permission, never by role name:

| Permission | What it allows |
| --- | --- |
| `submission:review:read` | The queue, and one submission's metadata and technical result |
| `submission:evidence:read` | Opening the submitted document and report |
| `submission:decision:write` | Starting a review, approving, rejecting, requesting a revision |
| `submission:comment:write` | Writing a review comment the author will read |

`ORGANIZATION_OWNER`, `ORGANIZATION_ADMIN` and `ORGANIZATION_REVIEWER` hold all
four. `TEMPLATE_MANAGER` holds none: writing the rules a document is measured
against and deciding a student's submission are different jobs.

The decision itself is one transaction over a locked row — read the current
status under `FOR UPDATE`, validate the transition, write the status, append
the event, append the comment the decision required. Two reviewers pressing
Approve and Reject at the same moment produce one decision and one conflict,
never two events disagreeing about what the institution said. An `If-Match`
style `expectedStatus` turns a stale screen into a visible conflict rather than
a silent overwrite.

`REJECTED` and `REVISION_REQUESTED` require a comment: they are the two the
author has to act on, and an institution that cannot say why has not told them
anything. Comments are immutable and are not decisions — writing one changes no
status.

## What Phase 14 does not do

No certificate issuance. No blockchain. No peer-review marketplace. No AI
making or influencing an institution decision. No scientific-merit scoring —
the reason codes are administrative, because PalCert cannot define what
"insufficient novelty" means across every institution and pretending to would
put PalCert's name on a judgement it did not make.

No organization access to private checks. No organization revenue share. No
submission fee: a submission is a handoff, not a purchase, and a decision has
zero ledger effect. Domain events are emitted; email delivery is not
implemented.
