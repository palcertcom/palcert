# SmartFix: verified DOCX formatting with optional AI planning

> PalCert may change deterministic document formatting, but it must never
> silently change academic meaning.

That sentence is the whole design. Everything below is a mechanism for keeping
it true when the code is wrong, the worker dies, the engine is upgraded, or
somebody edits their document between planning and paying.

SmartFix takes a **completed check**, works out exactly which failing rules it
could correct, simulates and rechecks the combined plan, and — only
when that preview resolves the whole standard and the user approves it —
produces a **new version** of their document, rechecks it automatically, and
charges only once the result is proved. The original is never modified.

---

## 1. The shape of a correction

```
completed check
      │
      ▼
  plan preview  ──────────────────────────────────────────────┐
      │  what would change, rule by rule, and what would not │
      ▼                                                       │
  user reads it and decides ◄─────────────────────────────────┘
      │
      ▼
  reserve or reuse AI planning reservation ──► SMARTFIX_EXECUTE
                          │
                          ├─ apply the approved plan (Python engine)
                          ├─ ingest the generated bytes (Phase 5 pipeline)
                          ├─ record the change manifest
                          └─ start the automatic recheck (an ordinary check)
                                   │
                                   ▼
                          recheck completes ──► SMARTFIX_FINALIZE
                                                    │
                                                    ├─ all standard rules resolved?
                                                    ├─ any regression?
                                                    └─ deliver + charge
```

Failure anywhere before delivery releases the reservation. Nothing is charged
and nothing becomes visible.

## 2. What SmartFix will and will not change

### The capability registry is the floor

`contracts/registries/smartfix-capabilities.json` is the single source of truth
for what the engine can change. The TypeScript constant is generated from it
and the Python engine reads it directly, so the two cannot disagree about what
the user approved.

A rule's `autofix: SAFE` is a **ceiling** set by whoever authored the standard:
it says the change _would_ be safe if PalCert could make it. The registry says
whether PalCert can. Both have to agree. A property absent from the registry is
never edited, however the rule is labelled.

Registry **3**, engine **1.1.0**, adds run language (Latin and complex script),
text color, existing paragraph-style assignment, list start values, and native
floating-to-inline drawing conversion to the existing typography, spacing,
indent and section-geometry corrections. List starts clone numbering instances
so selected items stay together without editing other lists. Drawing conversion
preserves the stored extent and graphic, removes floating layout, and refuses
unknown extensions or nonzero relative dimensions that require a layout engine.
A paragraph-style assignment never edits the shared style definition.

Engine **1.2.0** adds general AI-assisted formatting planning. It has no document,
institution or standard-specific branches. The standard's original scopes,
operators, expected values, tolerances and edit permissions remain authoritative.
AI selects formatting values; the engine resolves every affected element,
validates the values against the original rules, applies them to a copy, and
independently rechecks the entire standard. A provider response is never a verdict.

### Three things it refuses outright

A refusal is a property of the _document_, not of any rule, so the plan records
one code and carries no actions at all:

| Code                                   | Why                                                                                                                                                                       |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SMARTFIX_TRACKED_CHANGES_UNSUPPORTED` | A document under revision marks is a conversation between an author and a supervisor. Writing into it either joins that conversation under PalCert's name or bypasses it. |
| `SMARTFIX_DOCUMENT_PROTECTED`          | The author asked Word to forbid editing.                                                                                                                                  |
| `SMARTFIX_SIGNED_DOCUMENT_UNSUPPORTED` | Any edit invalidates the signature, which is the signature working.                                                                                                       |

### Operators that name a single value, and nothing else

SmartFix has to know what "fixed" means before it edits anything.

| Operator                                                                    | Treatment                                                                                                                                |
| --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `EQUALS`, `>=`, `<=`, `BETWEEN`                                             | A single reachable target. Planned.                                                                                                      |
| `>`, `<`                                                                    | `AMBIGUOUS_TARGET`. The nearest satisfying value depends on a step size nobody declared.                                                 |
| `IN`, `NOT_IN`, `CONTAINS`, `NOT_CONTAINS`, `MATCHES_PATTERN`, `NOT_EQUALS` | `AMBIGUOUS_TARGET`. Choosing a member of a set or a match for a pattern would be PalCert deciding what the author's document should say. |
| `EXISTS`, `NOT_EXISTS`                                                      | `CONTENT_CHANGE_REQUIRED`. The only remedies are writing or deleting content.                                                            |

Counts (words, pages, paragraphs, tables), pagination and document metadata are
refused by name, with a reason the UI can translate — because "unsupported" is
a worse answer than "a word count is an outcome of what you wrote".

The table above describes planning without AI. With explicit AI planning,
ambiguous operators may receive a concrete value for an already-supported
formatting property. For example, `IN [Arial, Times New Roman]` can select Arial,
and an exclusive minimum can select a representable value above the minimum.
The compiler checks the unchanged original operator after unit conversion and
OOXML rounding. Incorrect values, unsupported properties, forbidden element
types, content changes, `autofix: NONE/ADVANCED`, and non-deterministic rules are
still refused. AI does not broaden its own permissions or bypass missing evidence.

### One price for AI planning and correction

AI planning is a bundled billable operation under ADR-0149, not a separately
priced product. The UI displays the SMARTFIX quote and available balance before
the user confirms. `smartfix_planning_reservations` binds the authenticated owner,
completed check, quote-funded purchase and eventual immutable plan. The eventual
request reuses the reservation ID and purchase; approval does not reserve again.

Quote-row and reservation-row locks serialize retries, approval and cancellation.
A retry of a completed plan returns the same plan. A concurrent in-flight retry
is refused with its reservation ID; it can retry the same quote after completion.
Before token counting and each generation the service checks live credit.
Incomplete/refused/failed planning releases the purchase. Unapproved plans can be
cancelled through `POST /smartfix/plans/:planId/cancel`; the sweep releases expired
plans and recovers planners abandoned beyond the 90-second deadline plus 30-second
grace. Sweep candidates are checked again under lock. Approval transfers settlement
to the existing correction lifecycle. No preview is charged, and only successful
independent full-standard recheck and delivery capture the single SMARTFIX purchase.

The additive migration enforces owner isolation, immutable bindings, legal states,
release on terminal planning failure/cancellation and atomic consumption with the
correction request. Existing deterministic plans keep their original purchase flow.

### AI planning and convergence

The plan UI has an unchecked, per-request consent option. Selecting it permits
sharing formatting measurements and the selected standard rules with the
configured external provider. It does not grant general AI-review consent.
Document bytes, paragraphs, images, titles and prose are not sent; format values
and rule scopes are untrusted data in the user prompt. Instructions are static.
Content/unsupported rules disclose only identifiers, counts and outcomes.

The first preview contains original violations before any default changes are
simulated. This lets AI select compatible values for overlapping requirements,
such as font size 12 and font size at least 10. Each response contains only
`ruleCode`, `kind`, and `value`; it cannot supply XML, executable code, node IDs,
replacement prose, verdicts or altered rules. The engine compiles proposals from
the original bytes on every round, expands them across all matching elements,
and uses the existing dependent-change simulation. Remaining outcomes and
rejection feedback return to the provider for another proposal.

The loop stops when every rule is PASS/NOT_APPLICABLE, proposals stop changing,
or three rounds finish. All applicable rules must pass; an unknown, missing,
errored or unresolved rule prevents a complete plan. Purchase additionally
requires AI provenance `stopReason: VERIFIED`; the final ordinary recheck still
decides delivery and charging. No AI call takes place after the user approves
the immutable plan. Provider outages do not silently fall back to another
provider or to a purported AI result.

Resource limits: 512 source rules, the lesser of configured/120,000 context
characters and configured/24,000 input tokens per round, at most configured/8,000
output tokens, three generations, and a shared 90-second cancellation deadline
across token counting, generation and engine calls. The `/checks/:checkId/ai-plan` endpoint is
limited to three requests per minute per existing throttle tracker. Oversized
standards are refused rather than truncated. Distinct observed format values
are sampled to eight per rule with a truncation indicator; planning and checking
still use every fact. Deterministic planning is free. AI planning confirms a
SMARTFIX quote and reserves that price before any external provider call. Call start/completion/error audit events contain identifiers,
model, context digest and usage counts, never prompts or document text.

The hashed plan stores provider/model, round count, stop reason and token usage.
The format has an optional provenance field and remains compatible with historic
artifacts. Engine 1.1.0 plans cannot execute as 1.2.0 plans. Deploy API, worker,
web and document-engine together, drain existing corrections, and create fresh
plans. The proxy deadline must exceed the 90-second application deadline (the
repository release proxy uses 120 seconds). Apply migration
`20261023000000_smartfix_ai_reservations` before starting the new API/worker.
Existing AI configuration selects the provider/model; no new credential is needed.

This is not a universal Word layout editor: unsupported table geometry, visual
pagination, content changes and AI/manual-only assessment rules remain explicit
blockers. A complete result means all applicable rules of the exact published
standard have passed the evaluator, not a visual or academic acceptance claim.

## 3. Correctness mechanisms

### Targets are expanded, not sampled

The Phase 6 extractor emits **one fact per distinct value per paragraph**, so a
paragraph whose five runs are all 11 pt produces a single fact located at the
first of them. Planning only that run would leave four behind and fail the
recheck for reasons the manifest could not explain.

So a run-level fix expands to every run in the same paragraph currently holding
the same value — exactly the set of runs the fact stood for.

### Numeric targets are round-tripped before they are planned

WordprocessingML stores page geometry in whole twips, so 30 mm is 1700.79 twips
and a document can only hold 1701 — which reads back as 30.004 mm.

Every numeric target is therefore converted into the units the document will
really hold, converted back, and **re-evaluated with the same operator the
check used**. A target that would still fail after rounding is reported as
`SMARTFIX_TARGET_NOT_REPRESENTABLE` and never planned: it would look like a
fix, cost the user money, and fail the recheck.

### Script channels are part of the capability

WordprocessingML keeps Latin, complex-script and East Asian typography in
separate attributes and elements. Writing `w:sz` for an Arabic paragraph
changes nothing a reader can see while the manifest claims the size was
corrected — the single most dangerous way for this engine to be wrong. The
channel is carried on every run-level capability and never guessed.

### Targeted formatting, never a shared style rewrite

The property is written on the run, the paragraph or the section the plan
named. Correcting one paragraph's font by editing `Normal` would silently
restyle the whole thesis, including the parts that were already right.

### One bounded, source-bound preview

Planning simulates the edits and evaluates every source-standard rule. If a
style assignment exposes a new indentation or font mismatch, the planner adds
that correction to the same plan and reapplies it to the original bytes. At
most three merge rounds are allowed, followed by verification of the final
combined plan. Conflicting targets are refused; unresolved, errored, manual and
AI-assisted rules remain explicit blockers. No new actions are invented after
approval. The preview never saves intermediate document files. AI planning
reserves the correction price before provider work; deterministic planning does not.

Both the API and UI require a current-engine plan with only FIXABLE rows before
purchase. A stale 1.0.0 plan must be recreated. The author must still permit each
edit with `autofix: SAFE`; this release does not change any published standard.

### Everything, or nothing

The mutator resolves every action — locating the element and re-reading its
prior value — _before_ it writes the first one. A plan that cannot be applied
completely is not applied at all, because a half-corrected thesis is worse than
an uncorrected one.

### The output is proved, not asserted

Four projections of the package are computed identically before and after, and
the transformation is refused unless all four match:

- **visible text** — every character a reader sees, across every story
- **media** — images, fonts and embedded objects, by content
- **field instructions** — the code behind a table of contents or a page number
- **relationships** — what every part points at

Then every manifest entry is verified by **re-reading the corrected document**.
A planned action is an intention; only the output is evidence. An action that
silently did nothing is caught here rather than by the recheck.

### Nothing else in the package moves

Every entry PalCert did not edit is copied across verbatim, with its original
compression and ZIP metadata, and no wall-clock timestamp reaches the archive —
so the same plan over the same source produces the same bytes.

Re-serializing an edited XML part preserves the root element's start tag
byte-for-byte, because OOXML names namespace prefixes inside attribute _values_
(`mc:Ignorable="w14 wp14"`) and a renamed prefix leaves the file referring to a
namespace it no longer declares. Unambiguous nested declarations are preserved
too, including prefixes used only in `Requires`. Reserved `nsN` prefixes are
remapped safely; ambiguous rebinding and nested default namespaces are refused.

## 4. The commercial shape

SmartFix reuses the Phase 10 `SMARTFIX` product and the Phase 11 purchase
domain unchanged. There is one billing framework, because the customer only
ever has one question.

| Stage              | Request                | Purchase     | Charged                    |
| ------------------ | ---------------------- | ------------ | -------------------------- |
| Deterministic plan | — | — | No purchase or reservation. |
| AI plan | SMARTFIX | existing SMARTFIX quote | Reserve before AI, reuse on approval, capture only on verified delivery. |
| Start              | `RESERVED`             | `RESERVED`   | Nothing                    |
| Correcting         | `PROCESSING`           | `PROCESSING` | Nothing                    |
| Rechecking         | `RECHECKING`           | `PROCESSING` | Nothing                    |
| Validating         | `VALIDATING`           | `PROCESSING` | Nothing                    |
| Delivered          | `DELIVERED`            | `DELIVERED`  | The quoted amount, once    |
| Failed / cancelled | `FAILED` / `CANCELLED` | `RELEASED`   | Nothing, ever              |

Delivery now requires **every rule in the exact source standard** to PASS or be
NOT_APPLICABLE. Failed, missing, errored or indeterminate results block delivery,
including untargeted rules. This supersedes the earlier partial-delivery policy.
Historical deliveries are not relabelled; their recheck reports remain evidence.

### Delivery is one transaction

The corrected version becoming visible, the request becoming `DELIVERED` and
the reservation becoming a charge are one commit. There is no ordering of two
commits that is safe, so there is only one.

## 5. What the database refuses

Services can be bypassed; triggers cannot.

| Guarantee                                                         | Mechanism                                                                                                                                                                                                                        |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The original is never modified                                    | Phase 5 freezes a version's identity columns; `document_versions_origin_lineage` makes origin and lineage write-once on top of it                                                                                                |
| A correction always has lineage                                   | Same trigger: `SMARTFIX` origin requires a source version and a request, both the same owner's and the same document's                                                                                                           |
| An upload is never hidden from its owner                          | Same trigger                                                                                                                                                                                                                     |
| A correction is invisible until delivered, and visible once it is | `document_versions_smartfix_visibility`, deferred to COMMIT — both directions, so a later update of the version alone cannot withdraw a delivered correction                                                                     |
| No free check through the side door                               | `document_checks_require_purchase`, taught about `CheckPurpose`: a `SMARTFIX_RECHECK` must name a request that owns it, recheck exactly the version it produced, use the same standard version, and carry no purchase of its own |
| Purpose cannot be reclassified                                    | `document_checks_purpose_immutable`                                                                                                                                                                                              |
| Nothing delivered without proof and payment                       | `smartfix_requests_settlement`, deferred: a `DELIVERED` request must have a manifest, a `COMPLETED` recheck, a visible corrected version and a `DELIVERED` purchase                                                              |
| A failed correction is free                                       | Same trigger: `FAILED`/`CANCELLED` requires a `RELEASED` purchase, no captured holds, and a hidden output                                                                                                                        |
| A manifest cannot claim it changed the text                       | `smartfix_manifests_integrity_holds`: the four before/after digests must be equal, as a CHECK constraint                                                                                                                         |
| A manifest is evidence                                            | `smartfix_manifests_immutable`; `UPDATE` and `DELETE` revoked from the application role                                                                                                                                          |

## 6. The recheck

The automatic recheck is an **ordinary check** — same queue, same evaluation,
same report — with two differences enforced in the database:

- `purpose = SMARTFIX_RECHECK` and a `smartFixRequestId` naming the correction
- **no purchase of its own**, because the user already paid for it

It runs against the **exact historical StandardVersion**, even if that version
has since been archived or made private. Correcting against one set of rules
and rechecking against another would produce a report nobody could act on.

### What the recheck has to say

| Question                                                                     | Failure                         |
| ---------------------------------------------------------------------------- | ------------------------------- |
| Does every source-standard rule now PASS or become NOT_APPLICABLE?           | `SMARTFIX_TARGETS_NOT_RESOLVED` |
| Did any deterministic rule that passed before now fail or lose its evidence? | `SMARTFIX_REGRESSION_DETECTED`  |

Either one discards the correction entirely — it is not offered with a warning.
A document that trades one failure for another is not a correction.

AI-assisted rules are excluded from regression detection: calling a changed
model opinion a regression would discard a correct document because a language
model changed its mind. They still must satisfy the full-standard delivery gate;
an INDETERMINATE AI result never becomes PASS.

## 7. Where the work happens

| Concern                               | Home                                                              |
| ------------------------------------- | ----------------------------------------------------------------- |
| Planning, mutation, proofs            | `services/document-engine/app/smartfix/` (Python)                 |
| Contract, capability registry         | `contracts/schemas/smartfix.schema.json`, `contracts/registries/` |
| Purchase, request lifecycle, delivery | `apps/api/src/modules/smartfix/`                                  |
| Durable execution                     | `apps/api/src/worker/smartfix-job.handler.ts`                     |

The HTTP boundary to the engine is the same narrow one the analyzer draws:
bytes in, bytes out. No bucket, no object key, no URL, no database identifier.
A plan does not fit in an HTTP header, so bodies are framed explicitly — eight
bytes of length, that much JSON, then the document.

**No model is consulted anywhere in this phase.** Not to decide what to change,
not to perform a change, not to judge the result.

## PDF

There is no PDF SmartFix, and there is not going to be one in the shape of this
document. A PDF stores the finished page rather than the instructions that
produced it, so changing a margin would mean re-typesetting the document with a
layout engine PalCert does not have, and returning pages that differ silently
from the author's. A PDF check reports findings and says so; the correction
belongs in the source document. See
[ADR-0092](../adr/0092-pdf-is-an-inspection-format-not-a-smartfix-format.md)
and [`pdf-analysis.md`](pdf-analysis.md).
